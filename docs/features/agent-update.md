# Update Hermes from Settings (personal build)

Settings → Hermes agent checks `/api/hermes/update/check?force=true`. A git-updatable server with updates available offers an explicit, confirmed update action. Other installation methods show the server's guidance and cannot be updated from the phone. This action updates the *backend*, not the iOS app or the separate `hermes-push` plugin.

The confirmation warns that all sessions using that install may be interrupted, including dashboard and messaging gateways. `POST /api/hermes/update` is issued once only after confirmation. The server owns snapshot, apply, restart and verification; mobile never executes shell commands or retries the POST after an ambiguous transport failure. A rejected `{ok:false}` is a failure, not an accepted update.

Poll `GET /api/actions/hermes-update/status` while Settings is open, and use its action ID and receipt to identify the terminal outcome. Do not use network reconnection or a stale receipt as success. A missing/uncertain receipt is an unknown result; direct the user to the server logs. The update may outlive the iOS app's background window. Reopening Settings checks the latest server status, but must not attribute a prior update to this phone's action.

Ownership (E1): when the POST returns an action ID, the phone persists only that non-secret ID, scoped to the server origin + account (`notificationPreferenceScope`; never the token). It survives Settings dismissal and app relaunch; loading it under another scope clears it. On reopen with an owned ID, Settings performs a read-only status GET (no POST replay) and offers no new start until the owned action settles. Every status/check response is generation-fenced: confirming a start, dismissing Settings, rechecking and settlement each invalidate in-flight responses, so a slow startup recovery cannot relabel an owned update as external. A status only changes owned state when its `action_id` matches; final success requires that matching receipt with `finished_at` (an exit code alone is not success). If the server reports a different action ID, ownership is released as unknown (or external if that action is running). Server contract (hermes-agent `actions.py`): the status endpoint emits `action_id` ONLY from the `=== hermes-update completed <id> ===` marker, which is printed only on SUCCESS. A failed, partial or refused run reports `running:false, action_id:null` with a finished receipt `{outcome, started_at, finished_at}`, and an in-progress run reports `running:true, action_id:null`. So the phone also persists the non-secret time it sent the POST next to the owned ID, and settles an owned action without a matching ID as follows: (1) idle with a finished non-success receipt whose `started_at` is at or after that POST time (whole-second resolution) → `failed`, never success; ownership is cleared and responses are re-fenced. (2) Idle with no receipt, an unfinished receipt, an older receipt, an unmarked `success` receipt, or no recorded POST time → stays uncertain, and ownership is released as unknown on the user's explicit "Check update status" or after 3 consecutive authoritative idle observations (an unfinished receipt seen by the phone's own poll counts as in progress, not idle), so a failed update can never wedge the updater. (3) Running with a nil ID while owned (e.g. on reopen) is treated as possibly ours and polled. Success requires the matching action ID plus a finished receipt that is correlated with this phone's POST (`started_at` at or after the POST time, whole seconds), and the shown version is that receipt's `post_version`. Marker/receipt ordering window (hermes-agent `update_finish.py` / `update_cmd_fleet.py`): `_run_post_update_maintenance` prints the success marker FIRST; then the gateway fleet restarts, then `_verify_fleet_after_update` restarts the dashboard (`_refresh_dashboard_after_update`), and only at the end `finalize_update_receipt(...)` writes `latest.json`, with outcome `partial` if the restart was incomplete (exit 1), else `success`. So the status can legitimately read `running:false, action_id:<ours>` with the PREVIOUS run's finished receipt, and our own final outcome can still be `partial`. A matching ID with an uncorrelated receipt is "marker seen, receipt pending": the phone keeps ownership, shows the in-progress copy and keeps polling; it never settles success or failure from that receipt. A correlated `partial`/`failed`/`refused` receipt then settles `failed`; a correlated `success` settles success. If the receipt never arrives, the bounded poll ends uncertain (owned) and the explicit GET-only "Check update status" releases it as unknown, never success. Legacy owned IDs stored without a POST time can never be correlated: a matching-ID receipt is never success for them; they stay uncertain and are released as unknown on an explicit recheck or after 3 observations. (A receipt summary without `started_at`, from a server predating that field, is accepted for a matching ID only.) Updates started elsewhere stay external and are never shown as this phone's success. After an uncertain or external observation, "Check update status" is GET-only; a new start becomes available only after an authoritative idle status followed by a fresh availability check. HTTP calls use the existing connection authentication (token, cookie, or bearer).

The dashboard update endpoints authenticate a session but do not implement separate per-user administrator authorization; this is suitable for Michael's private token/Tailscale deployment, not a shared account where other authenticated users should be forbidden from updating the host. Server-side authorization is required before offering it to shared users.
